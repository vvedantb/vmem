## Overview

API keys provide programmatic access to vmem. Create and manage keys from **Settings → API → Keys** (`/settings/api/keys`).

## Key Format

Keys are prefixed with `vmem_sk_` followed by a base64url-derived suffix:

```
vmem_sk_a1b2c3d4e5f6...
```

## Creating a Key

1. Go to **Settings → API → Keys**
2. Click **Create key**
3. Enter a name (max 50 characters)
4. Copy the full key immediately — it is only shown once
5. The dashboard shows a masked version thereafter

## Storage

Keys are hashed for lookup and AES-GCM encrypted at rest (`v1:` format). Requires `ENCRYPTION_KEY` in Convex environment variables.

## Operations

| Function | Description |
| --- | --- |
| `apiKeys.createMy` | Create a new key (returns plaintext once) |
| `apiKeys.listMy` | List keys (masked) |
| `apiKeys.revokeMy` | Revoke a key |
| `apiKeys.revealMy` | Decrypt and reveal a key |

## Current Limitations

API keys are created and managed in the dashboard but are **not yet wired to a public HTTP REST API**. All first-party clients (web, extension, mobile) authenticate via Clerk through the Convex SDK.

MCP clients authenticate via OAuth + Bearer JWT, not API keys.

Usage recording (`recordUsageInternal`) exists for future metering but has no active callers.

## Future

When a public REST API is exposed, API keys will authenticate requests with Bearer token auth. The key management UI and encryption infrastructure are already in place.
