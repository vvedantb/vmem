## Overview

vmem is a monorepo with a Convex backend, Neo4j graph store, Vite web dashboard, Chrome extension, and Expo mobile app. First-party clients talk to Convex via the SDK; programmatic third-party access uses API key Bearer auth on Convex HTTP routes (`/api/v1/memories/*`).

## Monorepo Layout

| Path                    | Purpose                                         |
| ----------------------- | ----------------------------------------------- |
| `apps/web`              | Vite + React + TanStack Router dashboard        |
| `apps/mobile`           | Expo React Native app with offline local LLM    |
| `apps/chrome-extension` | Browser extension for ChatGPT/Claude/page saves |
| `apps/docs`             | Mintlify documentation site                     |
| `packages/backend`      | Convex functions, Neo4j actions, MCP server     |
| `packages/ui`           | Shared shadcn/ui component library (`@vmem/ui`) |

## Data Flow

### Writing a Memory

1. Client calls `memoryApi.createMemory` (Convex `authAction`)
2. Convex verifies Clerk identity, resolves active profile
3. Neo4j action creates the memory node with tags and embedding
4. Context prompt regeneration is scheduled (60s debounce)
5. Enrichment is scheduled server-side: an OpenRouter call tags the memory, links related memories, and extracts entities (see [Enrichment](/concepts/enrichment))

### Retrieving Memories

1. Client calls `memoryApi.retrieveMemories` with a natural language query
2. Neo4j runs hybrid retrieval: fulltext + vector + chunk + entity + graph expansion
3. Results are fused with RRF, scored for recency and confidence
4. Each result includes a **context trace** explaining the score
5. User settings (`aboutMe`, `preferences`) are merged in parallel

### MCP Implicit Memory

1. MCP client reads `vmem://context_prompt` at conversation start
2. Convex returns cached markdown profile (or placeholder on first read)
3. Background job regenerates the profile from pinned memories + recent activity
4. LLM sees user context without any tool call

## Authentication

All Convex functions use **Clerk** for identity. Protected functions use `authAction`, `authMutation`, or `authQuery` builders that inject `ctx.userId`.

MCP clients authenticate via **OAuth + PKCE** and receive a Bearer JWT signed with `MCP_JWT_SECRET`.

API keys (`vmem_sk_*`) are created in the dashboard and authenticate HTTP requests to `/api/v1/memories` (store, retrieve, update). Keys are AES-GCM encrypted at rest.

## Mobile Chat & Voice

The mobile app runs chat and voice on-device via **llama.cpp**, with an optional cloud mode via OpenRouter. Before each turn, relevant memories are retrieved from Convex and injected into the system prompt. The Convex backend chat surface is shared with other clients; the web dashboard does not expose a chat or voice UI.
