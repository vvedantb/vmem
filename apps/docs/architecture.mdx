## Overview

vmem is a pnpm monorepo with a Convex backend, Vite web dashboard, and Chrome extension. First-party clients talk to Convex with Clerk sessions. Programmatic third-party access uses API key Bearer auth on Convex HTTP routes (`/api/v1/memories/*`). Agents connect over MCP at `/mcp` (personal) and `/mcp/team`.

```
┌──────────────────────────────────────────────────┐
```

## Data Flow

### Writing a Memory

1. Client calls `memoryApi.createMemory` (Convex `authAction`) or `POST /api/v1/memories`
2. Convex verifies identity (Clerk session or API key) and resolves the profile
3. The row is written to the Convex `memories` table (tags, optional expiry, source metadata)
4. When `AI_GATEWAY_API_KEY` is configured, an embedding is stored for vector search
5. Context prompt regeneration is scheduled (60s debounce)

### Retrieving Memories

1. Client calls `memoryApi.retrieveMemories` or `POST /api/v1/memories/retrieve`
2. Hybrid ranking: Convex full-text + lexical overlap + optional vector similarity + tag/entity overlap + 1-hop `memoryLinks` neighbours + recency + temporal
3. Jev (`typesafe-ai/jev` through the AI SDK) reranks the top 20 hits when `AI_GATEWAY_API_KEY` is set on the Convex action (HTTP/SDK `judge: "off"` is ablation-only; MCP retrieve does not expose that flag). This runs from the retrieve **action** / **httpAction** — not from a query.
4. Each result includes a **context trace** explaining the score
5. User settings (`aboutMe`, `preferences`) are merged in parallel as `userContext`

### Nightly maintenance

One cron, `nightly maintenance` at 02:30 UTC (`convex/nightly.ts`), pages through users and runs one action per user on the `nightlyPool` workpool:

1. **Dream step** (`convex/dreaming.ts`), when `dreamModeAutomatic` is on. Per personal profile and per team profile the user owns, in bounded batches (at most 2,000 rows read per profile per run):
   - exact and same-page dedupe over the rows changed since the last run (the first run reads only the last 24 hours), merged at once into one keeper
   - Jev judges open `near_dup` write-time candidates; Qwen (thinking off) judges open `maybe_conflict` candidates. Confident merges and updates apply only with `dreamModeAutoAccept`, else they become proposals. At most 40 AI calls per user per night and $0.50 of dream AI per UTC day
   - rows past `expiresAt` become `expired`
   - stale browsing history, bookmarks and desktop rows are archived (`suppressedBy: "dream-decay"`), at most 500 per night, personal profiles only
2. **Rollups** (`convex/rollupActions.ts`), when `rollupsEnabled` is on: the day rollup for yesterday, then the ISO week on Sundays and the month on its last day.

A failed dream step is logged and does not block the rollups. Every dream change is a `dreamActions` row in the run's `dreamRuns` log and can be undone for 30 days. "Run dream mode" on the Dreaming page and MCP `dream_run` run the same dream step (once per hour).

Write-time candidates come from the embed step (`convex/dreamCandidates.ts`): one vector query per new embedding stores near pairs in `dreamCandidates`. Nothing merges at write time.

`DREAM_DISABLED=1` stops nightly and manual dreaming; rollups still run. `NIGHTLY_DISABLED=1` stops the whole cron. See [Dream Mode](/concepts/dream-mode) for the full rules.

### Retention crons

| Cron                             | Deletes                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------ |
| `purge expired traces`           | MCP traces and their details older than 7 days                                                   |
| `purge expired openRouter logs`  | AI log rows older than `OPENROUTER_LOG_RETENTION_DAYS` (no-op while unset)                       |
| `purge expired dream actions`    | Dream log rows 90 days after their 30-day undo window closed                                     |
| `sweep expired dream duplicates` | Duplicates a dream merge hid (`suppressedBy: "dream"`), once their 30-day undo window has passed |
| `purge old dream cleanup plans`  | One-off cleanup plans 30 days after the dry run                                                  |
| `purge dream candidates`         | Write-time candidates older than 30 days, or whose rows are gone or hidden                       |

All run hourly, 500 rows a batch (candidates: 200; duplicate sweep: 100). Only the duplicate sweep hard-deletes memories, through the normal delete path (links, mentions, embedding, usage and stat counters go too).

### MCP Implicit Memory

1. MCP client reads `vmem://context_prompt` at conversation start (personal connector only)
2. Convex returns cached markdown profile (or a placeholder on first read)
3. Background job regenerates the profile from pinned memories + recent activity
4. LLM sees user context without any tool call

## Authentication

| Surface                    | Auth                                              |
| -------------------------- | ------------------------------------------------- |
| Web app / Chrome extension | Clerk session → Convex `authAction` / `authQuery` |
| HTTP `/api/v1/memories/*`  | `Authorization: Bearer vmem_sk_…`                 |
| MCP `/mcp` and `/mcp/team` | Clerk OAuth access token                          |

Protected Convex functions use `authAction`, `authMutation`, or `authQuery` builders that inject `ctx.userId`. There is no `MCP_JWT_SECRET` — MCP verifies the Clerk OAuth token directly.

API keys (`vmem_sk_*`) are created in the dashboard and AES-GCM encrypted at rest.
