## Overview

vmem is a pnpm monorepo with a Convex backend, Vite web dashboard, and Chrome extension. First-party clients talk to Convex with Clerk sessions. Programmatic third-party access uses API key Bearer auth on Convex HTTP routes (`/api/v1/memories/*`). Agents connect over MCP at `/mcp` (personal) and `/mcp/team`.

## Data Flow

### Writing a Memory

1. Client calls `memoryApi.createMemory` (Convex `authAction`) or `POST /api/v1/memories`
2. Convex verifies identity (Clerk session or API key) and resolves the profile
3. The row is written to the Convex `memories` table (tags, optional expiry, source metadata)
4. When `AI_GATEWAY_API_KEY` is configured, an embedding is stored for vector search
5. Context prompt regeneration is scheduled (60s debounce)

### Retrieving Memories

1. Client calls `memoryApi.retrieveMemories` or `POST /api/v1/memories/retrieve`
2. Hybrid ranking: Convex full-text + lexical overlap + optional vector similarity + tag/entity overlap + 1-hop `memoryLinks` neighbours + recency + temporal
3. Jev (`typesafe-ai/jev` through the AI SDK) reranks the top 20 hits when `AI_GATEWAY_API_KEY` is set on the Convex action (HTTP/SDK `judge: "off"` is ablation-only; MCP retrieve does not expose that flag). This runs from the retrieve **action** / **httpAction** — not from a query.
4. Each result includes a **context trace** explaining the score
5. User settings (`aboutMe`, `preferences`) are merged in parallel as `userContext`

### Dream Mode

1. The dream pass (Convex **action**) clusters visible memories with `clusterNearDuplicateMemories`
2. When `AI_GATEWAY_API_KEY` is set, Jev annotates each cluster (merge noul, keeper, auto-accept). Missing key or Jev errors **fail-open** to the heuristic (same spirit as retrieve). Jev never skips creating a proposal.
3. Every heuristic cluster becomes an inbox **merge** proposal. Auto-accept still materializes only when Jev marks the merge safe (or when Jev fail-opens)
4. Jev does not write merged title/content or dream portraits — AI Gateway / the existing generative path still owns prose

### MCP Implicit Memory

1. MCP client reads `vmem://context_prompt` at conversation start (personal connector only)
2. Convex returns cached markdown profile (or a placeholder on first read)
3. Background job regenerates the profile from pinned memories + recent activity
4. LLM sees user context without any tool call

## Authentication

| Surface                    | Auth                                              |
| -------------------------- | ------------------------------------------------- |
| Web app / Chrome extension | Clerk session → Convex `authAction` / `authQuery` |
| HTTP `/api/v1/memories/*`  | `Authorization: Bearer vmem_sk_…`                 |
| MCP `/mcp` and `/mcp/team` | Clerk OAuth access token                          |

Protected Convex functions use `authAction`, `authMutation`, or `authQuery` builders that inject `ctx.userId`. There is no `MCP_JWT_SECRET` — MCP verifies the Clerk OAuth token directly.

API keys (`vmem_sk_*`) are created in the dashboard and AES-GCM encrypted at rest.
