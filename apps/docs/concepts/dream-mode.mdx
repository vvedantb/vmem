---
title: "Dream Mode"
description: "Nightly cleanup of duplicates, outdated facts and stale browsing history"
---

Dream Mode cleans your memory while you sleep. It merges duplicates, expires old rows, archives stale browsing history and asks an AI judge about rows that look alike or disagree. Every change it makes can be undone for 30 days. After that, duplicate copies hidden by a merge or an AI-judged update are permanently deleted; archived and expired rows are kept.

## When it runs

- **Nightly.** One cron, `nightly maintenance`, runs at **02:30 UTC** for every user (`convex/crons.ts`, `convex/nightly.ts`). For each user it runs the dream step first, then [rollups](#rollups), so the day summary reads cleaned data. A failed dream step is logged and does not stop the rollups. There is no per-user schedule time.
- **Now.** **Run dream mode** on the Dreaming page and the MCP [`dream_run`](/mcp/tools) tool run the same pass. Manual runs are limited to one per hour and send no notification.

A run covers your personal profiles and the team profiles where you are the team owner (the owner's settings apply). Decay runs on personal profiles only.

## What one run does

The pass runs per profile, in batches of 100 rows. It reads at most 2,000 rows per profile per run. When it stops at a limit, the run is `partial` and the next run continues from where it stopped.

1. **Exact and same-page dedupe (deterministic).** Rows created or updated since the last run are grouped with their exact-hash and source-key peers (same page, same connector item). Each group merges into one keeper: a pinned row wins, else the oldest row. These merges apply at once, with undo.
2. **Near-duplicate judge (AI).** Open `near_dup` candidates go to Jev (`typesafe-ai/jev`).
3. **Conflict judge (AI).** Open `maybe_conflict` candidates go to Qwen, with thinking off.
4. **Skill drafts (AI).** When a row of the change window records something that worked, one Qwen call may draft reusable skills. They wait as `skill` proposals (see [Skill drafts](#skill-drafts)).
5. **Expire.** Active rows past `expiresAt` become `expired`. Pinned rows are not touched.
6. **Decay.** Stale browsing rows are archived (see [Decay](#decay)).
7. **Tag consolidation.** Tags that are the same web site spelled differently (`wwwyoutubecom`, `youtubecom`) merge into one brand tag (`youtube`). The pass reads the whole profile (up to 50,000 rows) and retags only the memories that carry a merged tag. Then, when `dreamModeUseAi` is on and the deployment has `AI_GATEWAY_API_KEY`, Jev judges a few look-alike tags (`machine-learning`, `machinelearning`) in groups of up to four, with at most 5 calls per run. It merges only tags that Jev rates the same, into the most used one. It skips the AI step when AI is off, no key is set or the daily dream budget is spent; the host-name merge still runs. It cannot be undone; the tag is not stored elsewhere. Running it again merges nothing new. New memories get the brand tag at write time, so `www.youtube.com` is stored as `youtube`.
8. **Log.** The run and each change are stored in `dreamRuns` and `dreamActions`. After a nightly run that changed something, you get an inbox notification.

### First run of a profile

The first run of a profile only reads rows created or updated in the **last 24 hours**. It does not backfill the whole profile. Older duplicates wait for the [one-off cleanup](#one-off-cleanup), which needs the owner's approval.

## AI judge

### Write-time candidates

When a memory gets its embedding, one vector query finds its 3 nearest rows in the same profile. Nothing merges at this point. The pair is stored as a candidate in `dreamCandidates`:

| Kind             | Rule                                                       | Judge |
| ---------------- | ---------------------------------------------------------- | ----- |
| `near_dup`       | cosine similarity ≥ 0.97 and the same memory type          | Jev   |
| `maybe_conflict` | cosine similarity 0.88–0.97 and at least one shared entity | Qwen  |

Candidates older than 30 days, or whose rows are gone or hidden, are purged hourly.

### What a verdict does

| Verdict         | Result                                                                                                                                                                                                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `duplicate`     | Merge. Applied at once only with `dreamModeAutoAccept` and confidence ≥ 0.9, else a `merge` proposal.                                                                                                                                                                                                                                           |
| `update`        | The newer row replaces the older one (newest wins, by `createdAt`). Applied at once only with auto-accept, confidence ≥ 0.9 and the same source family (so a browsing row never replaces an agent fact), else an `update` proposal. When the judge names the older row as the keeper, the newer row is kept and the change waits as a proposal. |
| `contradiction` | Always a `contradiction` proposal. You pick the row to keep.                                                                                                                                                                                                                                                                                    |
| `unrelated`     | The candidate is dropped.                                                                                                                                                                                                                                                                                                                       |

A failed call changes nothing. A new proposal is not created when a pending proposal already covers one of the rows. Approving a dream `merge` or `update` proposal runs under the same dream run, with undo. See [Proposed Updates](/concepts/proposed-updates).

### Outcomes

Dream Mode reads an outcome from each row: tags such as `success`, `fixed`, `failed`, `reverted` (also with an `outcome:` prefix), else the text (`PASS` / `FAIL`, "worked", "failed", "did not work", `Error:`, "reverted", "rolled back"). When a row of a conflict pair has an outcome, the judge sees it and prefers what worked: a row whose approach failed does not replace one that worked, unless it says that the same approach stopped working. With no outcome, the prompt is the same as before.

### Skill drafts

When the change window holds a row whose approach worked, one call per profile reads up to 12 rows with an outcome (what worked first) and may draft at most 2 skills. A draft needs a direct trigger ("Use when a task names …" / "Use when a task asks to …"), 3 to 10 imperative, general steps and at least one source that worked. What failed becomes a labelled **Pitfalls** list in the skill.

Before a draft is proposed, it goes through the same rules as the frontiermemory eval (`engine/memory/skills/`): the safety filter drops a skill that recommends bypassing a safeguard (hooks, tests, lint, CI, TLS, secrets, force-push, broad deletes), and the dedupe drops a near-duplicate of your skills, of pending or rejected skill proposals, or of an earlier draft.

A draft is never published, also with auto-accept. It waits on the Proposals tab as a `skill` proposal. **Create skill** adds it to your skills (the team's skills for a team profile, origin `dream`). Reject drops it. The source rows are not changed.

### Caps and budget

| Limit                                      | Value |
| ------------------------------------------ | ----- |
| `near_dup` calls per user per night        | 25    |
| `maybe_conflict` calls per user per night  | 15    |
| Skill draft calls per user per night       | 2     |
| AI calls per user per night (all profiles) | 42    |
| Dream AI budget per UTC day (all users)    | $0.50 |

The budget guard sums today's `openRouterLogs` cost for feature `dream`. The one-off cleanup spends from the same budget. When a cap or the budget is reached, the AI steps stop, the run is `partial` and the open candidates wait for the next night.

The AI steps run only when `AI_GATEWAY_API_KEY` is set on the deployment and `dreamModeUseAi` is on. Without them, only the deterministic steps run.

## Decay

Decay archives browsing rows that you do not use. A row is archived only when all of these are true:

- it comes from a low-prior source: browsing history, bookmarks or desktop capture
- `lastVisitAt` is more than 30 days ago
- `visitCount` is at most 2
- `usefulnessScore` is below 0.2 (a row with no score yet is kept)
- it has no retrieve, search or context-pack hits
- it is `active` (a pinned row never decays)

Archived rows get status `suppressed` with `suppressedBy: "dream-decay"`. At most 500 rows are archived per profile per night. Each archive can be undone for 30 days.

Decay runs only after the profile has a previous successful run (`ok` or `partial`) or an applied one-off cleanup. So a new profile is never decayed on its first night. Decay is off for team profiles, because shared rows are not one person's history.

## The Dreaming page and undo

The **Dreaming** page (`/{profileId}/dreaming`) has two tabs. **Proposals** is the default and lists pending [proposals](/concepts/proposed-updates) to approve or reject; its label shows the pending count. **History** lists the runs with their counts. The page header has **Scan for duplicates** and **Run dream mode**. You can undo one action or a whole run for **30 days**. Undo restores the before-snapshot of each row.

After the 30 days, an hourly sweep permanently deletes the duplicate copies a merge hid (`suppressedBy: "dream"`) and the rows an AI-judged merge or update hid (`suppressedBy: "dream-ai"`). Archived (`"dream-decay"`) and expired rows are kept hidden. Once a hidden copy is gone, undo refuses the whole action or run and changes nothing. The log rows are purged 90 days after the undo window closes. Hidden rows never count in the dashboard stats. MCP [`dream_history`](/mcp/tools) reads the last 10 runs (counts only).

Merged rows show where they came from ("merged from") on the memory.

## One-off cleanup

Nightly runs never read the full history. Duplicates that existed before Dream Mode are handled by a one-off cleanup in two steps:

1. **Dry run.** **Scan for duplicates** on the Dreaming page (your personal profile only, after a confirm dialog), or an operator runs `npx convex run dreamCleanup:dryRunForUser '{"clerkUserId":"user_…"}'`. It pages every memory of the profile (up to 50,000), groups exact-hash and same-page rows, and clusters near-duplicates over all eligible rows. Two memories are near-duplicates when a vector search finds them at cosine similarity ≥ 0.85, or when they share an entity that at most 6 memories mention. The search reads the 8 nearest hits of each memory; the memory itself is one of them. This vector floor applies to this scan only and is lower than the nightly `near_dup` rule (0.97); the AI still decides. Clusters are transitive (A like B and B like C give one cluster A, B, C) and hold at most 6 memories; a larger cluster splits into connected parts. The AI judges each cluster in one call (the gateway chat model, thinking off): which memories are duplicates, which one to keep (it keeps its id) and one merged text with every fact of the merged memories. It can leave out a memory that is not a true duplicate. A pinned memory is never removed. When a merged memory is longer than 3,000 characters, the AI does not see all of it, so the keeper keeps its own text. Up to 500 calls per scan (`jevMaxCalls` can only lower this). A scan that reaches the limit or the daily AI budget is `partial`. The next scan reuses the verdicts of the last plan (merged text included) for clusters with the same members and judges only the rest. It reuses only verdicts of this cluster judge: clusters from an older plan of the pair judge are judged again once. Errors are asked again. The web scan skips the AI when `dreamModeUseAi` is off. Nothing changes. The plan is stored in `dreamPlanGroups` for 30 days. A new scan is refused while one runs and within an hour of the last one. To see the cluster count before a scan, an operator runs `npx convex run dreamCleanup:countCandidatesForUser '{"clerkUserId":"user_…"}'`. It uses the same rules, makes no AI call, needs no key and writes nothing.
2. **Apply.** The plan shows as a card above the Dreaming page tabs. Nothing is applied until the owner reviews it and chooses **Clean up**. Deterministic groups merge with undo. Each AI-flagged cluster goes to the Proposals tab as one `merge` proposal: all its memories and the merged text. You can untick memories to leave them out (the kept memory stays ticked). Approving gives the kept memory the merged text and hides the other ticked memories, with undo for 30 days; undo also restores the old title and content. When the last batch ends, the same tag consolidation as step 7 runs on the profile.

## Settings

Settings → Preferences → Dream Mode. MCP `settings_update` takes the same fields.

| Setting               | Default                                         | Effect                                                                                                              |
| --------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `dreamModeAutomatic`  | on                                              | Nightly dreaming. Off: only manual runs.                                                                            |
| `dreamModeDecay`      | on                                              | Archive stale browsing history, bookmarks and desktop rows.                                                         |
| `dreamModeUseAi`      | on when the deployment has `AI_GATEWAY_API_KEY` | Ask the AI judge about candidates. Off: only exact and same-page merges.                                            |
| `dreamModeAutoAccept` | off                                             | Apply AI merges and updates with confidence ≥ 0.9 at once. Off: they wait as proposals. Contradictions always wait. |

## Operator switches

| Variable             | Effect                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `DREAM_DISABLED=1`   | Stops nightly and manual dreaming. `dream_run` returns `reason: "disabled"`. Rollups still run. |
| `NIGHTLY_DISABLED=1` | Stops the whole nightly cron: dreaming and rollups. Manual dream runs still work.               |

See [Environment Variables](/environment#nightly-jobs-optional).

## AI usage logs

Every AI call is logged to `openRouterLogs` and shows on the Usage page:

| Usage label | Calls                                                                             |
| ----------- | --------------------------------------------------------------------------------- |
| Dreaming    | Nightly near-duplicate and conflict judges, skill drafts, one-off cleanup judge   |
| Rollups     | Day, week and month rollup summaries                                              |
| Jev         | Jev calls from retrieve, context pack, related memories and skill recommendations |

Jev calls go through the Vercel AI Gateway with `disallowPromptTraining`, so they only route to providers that do not train on prompts. They do not ask for request-level zero data retention, because that needs a Vercel Pro or Enterprise plan. `dataPolicy: "zdr"` stays opt-in in `engine/llm/systemOneClient.ts`.

## Rollups

Rollups are short activity summaries per profile. They are opt-in: Settings → Preferences → **Daily summaries (rollups)** (`rollupsEnabled`, default off). They need `AI_GATEWAY_API_KEY`.

After the dream step, the nightly run writes the **day** rollup for yesterday (UTC) from that day's memories and MCP tool traces. A quiet day makes no call and writes no row. On a Sunday it also writes the **ISO week**, and on the last day of the month the **month**. Weeks and months are built only from stored rollups. A failed call is tried once more, then the row is stored as failed.

MCP [`memory_timeline`](/mcp/tools) reads rollups, and `context_pack` adds them when the task names a time window. Reading never calls an LLM.

## MCP traces

Each MCP tool call and resource read is stored as a trace: tool, profile, status, duration, a short summary, sanitised and capped arguments, result IDs and a result preview. The **Traces** page shows them. Traces older than **7 days** are deleted by an hourly cron, 500 rows a batch.
