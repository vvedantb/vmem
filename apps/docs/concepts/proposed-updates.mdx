## The Problem

Imagine a user tells an AI assistant: "I prefer Python." A week later, they say: "Actually, I've switched to TypeScript." What should the memory system do?

Most systems silently overwrite. The old memory is gone — no record of what changed or why.

## Designed behaviour

When vmem detected that new information conflicted with an existing memory, it created a **proposed update** instead of overwriting. The original memory stayed unchanged until you approved the change.

```
New memory extracted: "User prefers TypeScript"
  → vmem detects conflict with: "User prefers Python"
  → Creates a proposed update (pending)
  → User reviews and approves/rejects via Dreaming → Proposals or API
```

Instruction **update** (`PATCH { instruction }` / SDK `update()`) extracts facts, retrieves related rows, and **supersedes** the prior memory (status `suppressed`, `updates` link) instead of inserting a duplicate. Retrieve therefore sees the latest fact even when stale and current share a timestamp.

[Dream Mode](/concepts/dream-mode) also writes proposals, in `source: "dream-mode"`. Exact and same-page duplicates merge at once each night, with 30-day undo, and make no proposal. The AI judge sends what it is not sure about to the Proposals tab:

- `merge`: Jev says two rows are duplicates. It applies at once only with `dreamModeAutoAccept` and confidence ≥ 0.9.
- `update`: the conflict judge says the newer row replaces the older one. It applies at once only with auto-accept, confidence ≥ 0.9 and the same source family.
- `contradiction`: the rows disagree. It always waits for you. On approve, pass `winnerMemoryId`; the other rows are superseded by it.

Approving a dream `merge` or `update` runs under the dream run that proposed it, so you can undo it on the Dreaming page History tab for 30 days. Dream Mode does not create a proposal when a pending proposal already covers one of the rows. The one-off cleanup also sends its Jev-flagged groups here as `merge` proposals. `listProposedUpdates` / `resolveProposal` persist in the `proposedUpdates` table.

The types below describe the proposal shape.

## Proposal Kinds

| Kind            | Description                                              |
| --------------- | -------------------------------------------------------- |
| `update`        | Replace memory content with proposed content on approve  |
| `delete`        | Delete the target memory on approve                      |
| `insight`       | Synthesize a new memory from connected sources           |
| `connection`    | Link related memories with a new relationship            |
| `contradiction` | Two rows disagree; you pick the one to keep (Dream Mode) |
| `anomaly`       | Surface unusual patterns in memory data                  |
| `merge`         | Collapse duplicate rows into one keeper (Dream Mode)     |
| `skill`         | A drafted skill; approving creates it (Dream Mode)       |

On `main`, only Dream Mode creates proposals (`merge`, `update`, `contradiction` and `skill`). The other kinds stay in the schema. A `skill` proposal carries `skill: { name, description, instructions }`; it changes no memory, so it never blocks another proposal on the same rows.

## Managing Proposals

### Via Dashboard

Go to **Dreaming → Proposals** (`/{profileId}/dreaming`; Proposals is the default tab). The old `/{profileId}/inbox/proposals` and `/{profileId}/proposals` URLs redirect there. The Inbox holds notifications only.

### Via API

```typescript
const proposals = await convex.action(
  api.proposedUpdateApi.listProposedUpdates,
  {},
);

await convex.action(api.proposedUpdateApi.resolveProposal, {
  proposalId: "proposal_abc",
  action: "approve", // or "reject"
});
```

See [Proposed Updates API](/api-reference/proposed-updates).
